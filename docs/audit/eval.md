# Audit: eval/ (red-team harness, load simulator, metrics, overhead and live checks), 2026-11-17, read-only, nothing run

Scope: F119 (red-team harness), F120 (load simulator), F121 (metrics export), F122 (agent overhead + live Google check), scenarios in `eval/scenarios/`. `eval/` is a test tool, but it runs attacks on lab PCs, holds the internal token and loads the real CCC, so mistakes here either damage a lab or produce wrong numbers for the thesis. There is **no screen test at all** (see I-EVAL-1).

| ID | Severity | File:line | Problem | Fix |
|---|---|---|---|---|
| I-EVAL-1 | High | eval/ (missing); harness/agent_overhead.sh:6 | There is no way to measure screen smoothness (fps, latency, bytes, CPU on the PC), which is the product's most important visible feature. `agent_overhead.sh` measures only the agent process, not `xephyguard-helper` where the streamer runs, and not while streaming. The red-team scenarios have nothing for screen (spoofed stream, plaintext :8082, idle-PC view). | Add a screen benchmark (headless fake capture to gateway to a headless viewer counting frames) and screen red-team scenarios; make the overhead script include the helper and a "streaming" phase. |
| I-EVAL-2 | High | simulator/fake_agents.py:40,98-111 | `self.seq = 0` on every start while `creds.json` makes the same PC identity persist across runs. The server de-duplicates by `seq` (DECISIONS #4), so a second run's events are acknowledged but dropped. The run reports good latency while ingesting nothing. | Start `seq` from a persisted counter (or from `ts`) and verify ingest by reading back event counts. |
| I-EVAL-3 | High | simulator/fake_agents.py:109-159 | Pass/fail uses only the p95 of successful requests. Errors (`self.errors`) do not fail the run, so 50 % failures can still pass. The measured value is POST response time, but the stated target is "visible on the dashboard in < 1 s". | Fail on error rate (> 1 %), and measure end-to-end (event ts to broadcast received on a Reverb listener). |
| I-EVAL-4 | High | harness/redteam.py:143 (+ :133-150) | `ccc_results()` is not wrapped: any `URLError`, timeout or HTTP 5xx raises and ends the whole run; results are written only at the end (:158), so every scenario done so far is lost. A raise also skips `cleanup` (:148-152), leaving the attack in place on the lab PC (tun device, `/etc/hosts` edit, a fake `ollama`, a changed clock). | Wrap the poll in try/except, write results after every scenario, and run cleanup in `finally`. |
| I-EVAL-5 | High | scenarios/linux.yaml:203-205 (+ :95-97, :195-196) | The clock scenario runs `sudo -n date -s '-2 hours'` on a real lab PC; if the cleanup fails (:205 falls back to `+2 hours`, which is wrong after a partial step) the PC keeps a wrong clock and its mTLS certificates, JWTs and logs break. `/etc/hosts`, `systemctl stop xephyguard-agent` are the same class. | Mark destructive scenarios `destructive: true`, require `--allow-destructive`, and restore from a value saved before the change. |
| I-EVAL-6 | Medium | harness/redteam.py:118-130 | The harness never checks that the target PC is in an active Test session, that it is a PC meant for testing, or that signatures are current. | I-EVAL-7 | Medium | harness/redteam.py:102-108 (+ :56-61) | `expect: {any: true}` counts any alert or blocked net event from that PC since `start`, so an unrelated alert (a real student action, another scenario's leftover) is recorded as "detected". `since_ms` is the harness clock but event times come from the CCC (1 s resolution, clock skew).
