# LabGuard — Project Description

A system that lets a university lab **control and observe AI usage on lab computers** while still giving students normal freedom to browse the web and learn. One central computer (the CCC) manages every student PC over the lab's IP network. It runs all the time, not only during tests, and a lab assistant should be able to set it up and operate it with a few clicks.

This document describes **what the project must have**. It is a specification, not a prompt. Where it says "decide", the implementer chooses and records the decision in `docs/DECISIONS.md`.

---

## 1. Goals

1. **Block** AI access on lab PCs during test mode, across every route practical to cover: websites, search-engine AI summaries, APIs, desktop apps, local models, IDE extensions, CLI agents.
2. **Detect** what cannot be blocked (phone on a hotspot, a hidden VM, a pasted answer) using behavioral signals.
3. **Monitor the whole lab time** with tiered intensity: light in normal labs, full in tests.
4. **Be easy for a lab assistant**: one installer per OS, auto-discovery, approve-don't-configure, schedule-driven modes.
5. **Produce research evidence**: measurable bypass rates, detection accuracy, overhead, exportable data for a paper.
6. **Respect privacy**: transparent to students, no capture of typed characters or clipboard contents, retention limits.

### Non-goals
- 100% prevention. A phone in a pocket always wins. The system makes AI use hard and visible, and reports its own gaps honestly.
- Automatic punishment. The system flags and explains; a human decides.
- Reading students' private content (typed text, clipboard text, personal messages).

## 2. Components and where they run

| Component | Runs on | Language / stack |
|---|---|---|
| **Agent** (service) | Every student PC (Windows + Linux) | C++20 |
| **Session helper** | Every student PC, inside the logged-in user session | C++20 (same codebase) |
| **CCC server** (dashboard, API, WebSocket, DB) | Central computer, Linux | Laravel 11, MySQL, Laravel Reverb (self-hosted WebSocket) |
| **Proxy + policy addons** | CCC | mitmproxy with Python addons |
| **DNS filter** | CCC | dnsmasq or Unbound with generated blocklists |
| **Firewall / gateway rules** | CCC | nftables, generated by the CCC installer |
| **Analysis service** | CCC | Python (pandas, numpy, scikit-learn) |
| **Instructor / assistant UI** | Any browser on the LAN | Nothing to install |

### Dataflow in one paragraph
The agent connects **outbound** to the CCC over WSS (mutual TLS), identifies itself, receives its current **policy** (mode, blocklists, thresholds, actions), and streams **events** (heartbeat, process, window, paste, key stats, network adapter, extension scan, file activity). The CCC stores events in MySQL, scores them, and pushes live updates to the dashboard. Commands (start session, change mode, isolate, message, kill process) travel back down the same socket. Student web traffic is forced through the CCC (gateway mode), where DNS and proxy layers block or log it. The instructor's browser only talks to the CCC.

## 4. Agent (C++)

### 4.1 Architecture
- **Core library** is platform-independent and fully unit-testable: protocol client, policy engine, rules matcher, event queue, config, scheduler client, logging.
- **Platform adapters** sit behind interfaces so each OS implements the same contract:
  `IProcessMonitor`, `IWindowMonitor`, `IClipboardMonitor`, `IInputTimingMonitor`, `INetworkMonitor`, `IFileWatcher`, `IExtensionScanner`, `IDeviceMonitor`, `IServiceHost`.
- Suggested libraries (decide): Boost.Asio/Beast or libwebsockets, OpenSSL, nlohmann/json, toml++, spdlog, SQLite3, Catch2 or GoogleTest. Build with CMake plus vcpkg or Conan.
- **Two processes per PC**:
  - **Agent service**: runs as SYSTEM (Windows) or root (Linux). Owns the connection, policy, rules, queue, tamper resistance.
  - **Session helper**: runs in the logged-in user's session. Collects what only a user session can see (active window, clipboard, key timing on Windows) and forwards to the service over a local IPC channel (named pipe / Unix domain socket, authenticated). The service launches the helper itself (Windows: `WTSQueryUserToken` + `CreateProcessAsUser`; Linux: systemd user unit or XDG autostart), so there is no user-editable startup entry to delete.

### 4.2 Monitoring features

| Signal | What is collected | Windows | Linux |
|---|---|---|---|
| Heartbeat | PC id, uptime, mode, agent version, logged-in user, clock offset every ~5 s | service timer | systemd service timer |
| Processes | Start/stop of anything matching AI signatures; periodic full snapshot (hash of list + diff) | ToolHelp snapshot, or ETW for start events | `/proc` scan + netlink proc connector |
| Listening ports | Local servers on known LLM ports (e.g. 11434, 1234) and unknown high-memory listeners | `GetExtendedTcpTable` | `/proc/net/tcp*` or netlink |
| Active window | App name, window title (title capture configurable, see privacy), focus changes | `SetWinEventHook` | X11 `_NET_ACTIVE_WINDOW` |
| Clipboard | Paste/copy **events**: size, line count, looks-like-code flag, source app. Content is never stored | `AddClipboardFormatListener` | X11 XFIXES selection events |
| Key timing | Aggregated per 5 s window: key count, inter-key interval stats, backspace ratio. **No characters** | low-level keyboard hook (timing only) | evdev from root agent (works on X11 and Wayland) |
| Network adapters | New adapter, new IP, tethering/RNDIS/USB-Ethernet, VPN adapter, second default route | `NotifyIpInterfaceChange` | netlink |
| Devices | USB storage and phones attach/detach | `RegisterDeviceNotification` | udev |
| IDE/editor extensions | Installed extension list for VS Code, VSCodium, JetBrains plugins, browser extensions | read extension dirs | read extension dirs |
| Local model artifacts | Files named `*.gguf`, `*.safetensors`, `*.ggml` in user dirs and removable media; Ollama/LM Studio model dirs | scheduled scan | scheduled scan |
| Virtualization | WSL, Hyper-V, VirtualBox, VMware, QEMU, Docker processes | `vmmem`, `wsl.exe`, VM binaries | `qemu`, `VBox*`, `docker`, `podman` |
| File activity | Work-folder size deltas and save timestamps (no content) | `ReadDirectoryChangesW` | inotify |
| GPU / memory spikes | Heuristic for local inference | NVML / DXGI | NVML / sysfs |
| Tamper | Service stop attempt, binary hash change, config change, clock change, certificate removal | SCM + file hashes | systemd + file hashes |

### 4.3 Detection rules
- All signatures live in **data files** (`data/signatures/*.yaml`), versioned and pushed from the CCC. Nothing is hard-coded.
- Seed lists (illustrative, to be extended and kept updatable):
  - **Processes**: `ollama`, `ollama_llama_server`, `llama-server`, `llama-cli`, `lmstudio`, `koboldcpp`, `gpt4all`, `jan`, `localai`, `text-generation-webui`; editors/agents `cursor`, `windsurf`, `zed`; CLI agents `claude`, `codex`, `gemini`, `aider` (match on executable and on `node`/`python` command lines).
  - **VS Code extension IDs**: `github.copilot`, `github.copilot-chat`, `anthropic.claude-code`, `continue.continue`, `codeium.codeium`, `tabnine.tabnine-vscode`, `sourcegraph.cody-ai`, `saoudrizwan.claude-dev`, `rooveterinaryinc.roo-cline`, `amazonwebservices.amazon-q-vscode`, `google.geminicodeassist`.
  - **Ports**: 11434 (Ollama), 1234 (LM Studio), plus a generic "HTTP server on localhost answering `/v1/chat/completions` or `/api/generate`" probe.
- Each rule has: id, severity, matcher, and action.

### 4.4 Actions (policy-controlled per mode)
`log` → `warn` (on-screen notice to student) → `kill` (terminate matched process) → `alert` (instructor notified) → `isolate` (CCC cuts that PC's network). Default for Test mode: log + warn + alert; `kill` is opt-in per rule.

### 4.5 Reliability and tamper resistance
- **Offline buffering**: events go to a local SQLite queue with monotonic sequence numbers; flushed on reconnect; CCC de-duplicates.
- **Clock**: agent reports offset against CCC time; CCC is the time authority.
- **Self-protection**: binaries and config root/SYSTEM-owned; Windows service recovery set to restart; Linux `Restart=always` with `WatchdogSec`; helper and service watch each other; hash check of own binary at start and periodically.
- **Heartbeat loss** (3 missed) becomes a "machine silent" alert. Distinguish clean shutdown (agent announces it) from kill or network cut.
- **Fail-safe behavior** when the CCC is unreachable: keep last known policy, keep logging locally. Network blocking is enforced at the CCC gateway, so an unreachable CCC means no internet rather than open internet.
- **Student transparency**: always-visible indicator (tray icon / notification) showing "Monitored by LabGuard, mode: Practice/Test".
- **Resource targets** (acceptance criteria, also reported in the paper): idle CPU under 1%, RSS under 30 MB, under 5 MB/hour uplink in Practice mode.

## 5. Network control (CCC side)

Layered, from cheapest to most invasive, so decryption is only used where needed.

1. **DNS sinkhole** (dnsmasq/Unbound): blocks AI domains for all lab clients. Block or redirect DoH/DoT providers so DNS cannot be bypassed. Lab PCs use only the CCC as resolver.
2. **SNI / domain filter** at the gateway: blocks TLS connections to listed domains **without decrypting**.
3. **QUIC control**: drop UDP 443 so browsers fall back to TCP and the other layers see the traffic.
4. **Selective TLS interception** (mitmproxy) only for hosts where content matters:
   - **Google/Bing/other search**: add `udm=14` (Web results) to Google search requests so AI Overviews are not returned; fall back to stripping the AI block from the response where that fails. Keep an automated test that checks this still works, because search markup changes.
   - Optional logging of URLs for permitted hosts (host + path, query text configurable).
5. **IDE and package traffic**: block extension marketplaces (`marketplace.visualstudio.com`, `open-vsx.org`) in Test mode; block known AI backends (Copilot, Cursor, Codeium, Tabnine endpoints).
6. **Seed AI domain list** (data file, community lists importable, hot-reloadable): OpenAI/ChatGPT, Anthropic/Claude, Google Gemini and AI Studio, Microsoft Copilot, Perplexity, DeepSeek, xAI, Mistral, Poe, Character.AI, Hugging Face chat, OpenRouter, Together, Groq, Phind, You.com, Blackbox, DuckDuckGo AI chat, Brave Leo, and API endpoints for the above.
7. **Browser built-in AI** (Edge Copilot sidebar, Chrome AI features): disable via managed browser policies in the install package. Verify policy names against current vendor docs.
8. **Other egress**: block known VPN/proxy/Tor endpoints and unknown outbound proxies in Test mode; allow only 80/443 to the proxy path.

### Network modes
- **Gateway mode (recommended)**: CCC has two NICs (WAN + lab LAN), is the lab's default gateway, enforces nftables policy. No per-PC proxy settings can be bypassed.
- **Proxy-only mode**: lab router redirects web traffic to the CCC proxy port. Weaker; documented as a fallback.

### Certificates
CCC generates an internal CA at first run. The CA certificate is installed on lab PCs by the agent installer (system store, plus browser stores where needed). Private key never leaves the CCC. Machines that do not trust the CA still get domain/SNI blocking, just not selective inspection.

## 6. Modes, sessions, scheduling

| Mode | Purpose | Network | Agent |
|---|---|---|---|
| **Always-on** | PC is on, no session | Log only, no blocking | Heartbeat, process/extension scan, adapter changes |
| **Practice** | Normal lab class | Configurable: log only or block chosen AI sites | Light behavior metrics, tampering and local-LLM alerts |
| **Test** | Lab test or exam | Full AI blocking, strict egress | Full behavioral logging, all rules active |

- **Session** = course + mode + profile + roster + time window. Created from a **timetable** (weekly recurrence) or manually with "Start session".
- **Profiles** are reusable policy bundles ("Practice: AI allowed, logged", "Test: AI blocked", "Exam: strict"). Editable in the dashboard.
- Mode switches are pushed live. On session end, blocking relaxes automatically and a report job starts.
- Override per PC (e.g. a student with an approved accommodation) is logged in the audit trail.

## 7. CCC server and dashboard

### 7.1 Roles
`admin` (setup, users, policy), `instructor` (sessions, reports), `assistant` (enroll PCs, start/stop sessions, view live). Audit log records every action with user and time.

### 7.2 Screens
1. **Live lab view**: seat-map grid (drag-and-drop layout editor), one tile per PC with status (clean / warning / alert / offline), active app, last event, score. Click a tile for a detail drawer: event timeline, processes, network log, key-rate chart, paste log.
2. **Alerts feed**: severity, rule, PC, time, acknowledge/comment, filter by session.
3. **Session control**: start/stop, switch mode, broadcast message to all or selected PCs, isolate/un-isolate a PC, kill a flagged process.
4. **Timetable and profiles**.
5. **Blocklist and signatures editor**: add domain/process/extension, import list, version history, hot reload to proxy, DNS, and agents.
6. **Enrollment**: "Add a PC" page (see §9), pending approvals, rename, retire.
7. **Roster**: import CSV (student id, name, login). Maps OS login to student for reports. Pseudonymization toggle for research exports.
8. **Reports**: per-student and per-session integrity report with score breakdown, timelines, paste and idle-then-burst events, blocked-attempt list. Export PDF and CSV.
9. **System health**: CCC services status, agent versions, certificate expiry, disk usage, "needs attention" list, built-in **doctor** results.
10. **Settings**: retention periods, privacy toggles, network mode, ethics banner text.

### 7.3 Backend
- REST API for the dashboard and the agent registration; WebSocket (Reverb) channels for live events and commands.
- MySQL, with partitioning or archiving for the events table (high volume).
- Queue workers for scoring, report generation, retention purge.
- Data model (minimum): `labs`, `seats`, `pcs`, `enrollments`, `agents`, `sessions`, `session_pcs`, `profiles`, `timetable_entries`, `rules`, `signature_versions`, `blocklist_entries`, `events`, `alerts`, `key_stats`, `paste_events`, `net_events`, `scores`, `reports`, `students`, `student_pc_assignments`, `users`, `audit_log`, `consents`.

## 8. Behavioral analysis

- **Features per student per session**: typing speed and burstiness, backspace ratio, paste-to-typed ratio, largest single paste, idle gap followed by large code growth, focus-switch rate, time outside the IDE, blocked-attempt count, adapter/device changes, process and extension flags.
- **Baseline**: normal Practice sessions give each student their own baseline; Test behavior is compared to it (z-scores). Fixed thresholds are the fallback for students with no baseline.
- **Scoring v1**: transparent weighted rule score (0 to 100) where every point is traceable to a named signal.
- **Scoring v2 (optional, behind a flag)**: Isolation Forest or similar per-student/per-cohort anomaly score, shown alongside v1, never replacing the explanation.
- **Output**: score, ranked reasons, confidence, and a plain statement of what was **not** observable. The UI always says "flag for human review".
- Guard against false positives: slow typists, copy of boilerplate from the assignment itself, accessibility tools. Exemptions are per-student and logged.

## 9. Setup (designed for a lab assistant)

### 9.1 CCC setup (Linux, once)
1. Ubuntu Server 22.04/24.04 LTS (or similar), two NICs for gateway mode.
2. Run `sudo ./ccc-deploy/install.sh`. It installs Docker, brings up Compose (app, MySQL, Reverb, proxy, DNS), generates the internal CA, writes nftables rules, and prints the dashboard URL.
3. Open the dashboard: **first-run wizard** creates the admin, names the lab, picks network mode, sets the lab subnet and CCC IP, sets retention and the student notice text.
4. Run `labguard-ccc doctor` (also in the UI). It checks IP forwarding, DNS resolution, proxy reachability, CA trust, time sync, ports, disk space, and explains each failure in plain language.
5. Fixed IP for the CCC (e.g. `192.168.10.2`) and DHCP reservations for lab PCs so IP and PC id stay stable.

### 9.2 Adding student PCs
The CCC serves an **"Add a PC"** page. It shows the one-time lab enrollment key and offers OS-specific installers. Agents then find the CCC by **auto-discovery** (mDNS or UDP broadcast) with the configured CCC address as fallback.

**Approve, don't configure**: a new PC appears as **Pending**; the assistant clicks Approve (or enables auto-approve for MACs on an allow-list). The CCC issues a per-PC token and client certificate. The assistant names the seat on the map.

### 9.3 Windows student PC
- **Installer**: single MSI (or NSIS/WiX, decide) installing:
  - `LabGuardAgent` Windows service (LocalSystem, automatic start, failure actions = restart).
  - `LabGuardHelper.exe` (launched by the service into each user session).
  - Internal CA into the LocalMachine trusted root store.
  - Config at `%ProgramData%\LabGuard\agent.toml`, admin-only ACL, plus logs directory.
  - Windows Firewall rule for the agent's outbound connection only.
- **Silent install**: `msiexec /i LabGuard.msi /qn ENROLL_KEY=<key> CCC_ADDR=<optional>`. Documented for GPO software deployment, Intune, PDQ, or imaging.
- **Lab hardening notes** (documented, applied by the installer where possible): standard-user lab accounts; disable WSL/Hyper-V features or monitor them; managed Edge/Chrome policies for built-in AI features; USB storage policy per lab choice; lock VS Code to a root-owned extensions directory.
- **Uninstall** requires administrator rights and raises a tamper alert.

### 9.4 Linux student PC
- **Packages**: `.deb` (primary, via CPack); `.rpm` optional. Installs:
  - `/usr/lib/labguard/labguard-agent` (root:root, 0755) and `labguard-helper`.
  - `labguard-agent.service` (systemd, `Restart=always`, `WatchdogSec`, hardening options that do not block required access).
  - Helper as a systemd user unit or XDG autostart.
  - Config at `/etc/labguard/agent.toml` (root, 0600); logs in `/var/log/labguard/`.
  - CA into the system store (`update-ca-certificates`), the NSS database for Chromium-based browsers, and Firefox through enterprise policy. Verify per browser version.
- **Install**: `sudo apt install ./labguard-agent_<ver>_amd64.deb` then `sudo labguard-agent enroll --key <key>`, or one line from the Add-a-PC page. For many PCs: an **Ansible role** reading a simple inventory.
- **Session type**: X11 gives full window and clipboard monitoring. On Wayland, window/clipboard visibility is limited by the compositor; key timing via evdev still works. The doc recommends X11 sessions for labs and the agent reports what it can and cannot see.
- **Lab hardening**: standard users without sudo, root-owned VS Code extensions directory (`--extensions-dir`), `ollama`/Docker/podman restricted or monitored, no unmanaged package installs.

### 9.5 Build and cross-platform notes
- Development happens on Linux. The agent core and Linux adapters build and test natively. Windows adapters cross-compile for a compile check with `mingw-w64` (or build on a Windows CI runner with MSVC). **Windows behavior must be tested on a real Windows machine or VM**; keep a documented test checklist.
- The Windows installer may need a Windows runner (WiX) or can use NSIS via `makensis` on Linux. Decide and document.
- Releases are produced by one script that outputs: agent `.deb`, Windows installer, CCC Compose bundle, checksums, and a version manifest. The agent supports **self-update from the CCC** with signature verification (stretch goal).

## 10. Security

- Agent to CCC: TLS 1.3, mutual authentication (per-PC client cert plus token). No listening port on student PCs.
- Identify machines by cert + MAC, never by IP alone.
- Rate limits and size limits on agent events; schema validation on every message.
- Passwords hashed (Argon2/bcrypt), roles enforced server-side, CSRF/XSS protection, audit log is append-only.
- Secrets (CA key, DB password, enrollment key) stored with restrictive permissions; the enrollment key is rotatable.
- Signed releases; agent verifies updates and signature databases.
- Threat model written in `docs/THREAT_MODEL.md`, covering bypass attempts a student could try: changing proxy settings, VPN/Tor, DoH, QUIC, USB boot, portable browser, hosts-file edits, killing the agent, changing the clock, WSL/VM, phone hotspot.

---

## 11. Privacy and ethics (built in, not bolted on)

- **Never stored**: typed characters, clipboard text, screen content, passwords, personal messages. Clipboard and keystroke data are reduced to numeric features on the PC and the originals discarded.
- Window titles: configurable (full / app-name only / off); default app-name only in Practice, configurable in Test.
- Tiered monitoring (§6) so normal lab time collects the minimum.
- Visible indicator and login banner stating what is collected and when.
- Per-student **consent record** for research use; research exports include only consenting students and are pseudonymized.
- Retention: raw events deleted after a configurable period (default one semester); aggregated reports kept longer.
- Student-facing page on the CCC explaining what is monitored.
- Statement text and consent form template in `docs/ETHICS.md`, for the university's ethics review.

## 12. Research and evaluation support

- **Experiment mode**: tags sessions as baseline or treatment, stores condition, group, and consent flags.
- **Red-team harness** (`eval/`): scripted bypass scenarios run against the live system, each recording blocked / detected / missed:
  - open a chatbot site, a Google search with AI Overview, a Copilot-style page;
  - change proxy settings, add a VPN or Tor, use DoH, use QUIC;
  - run Ollama or a llama.cpp binary, run it inside WSL or a VM;
  - install an AI VS Code extension, run a CLI agent, use a portable AI editor from USB;
  - paste a large generated block, type slowly after an idle gap;
  - kill or stop the agent, change the system clock, edit the hosts file;
  - phone hotspot (manual scenario with documented procedure).
- **Metrics produced automatically**: bypass rate per layer and overall, detection sensitivity/specificity (with labeled sessions), time-to-detect, false-positive rate on honest sessions, agent CPU/RAM/network overhead, student-experience survey hook.
- **Exports**: CSV/Parquet of events and scores, a results table generator for the paper, reproducible scripts.
- Comparison harness for the C++ agent against a simple Python prototype for the overhead section (optional).

## 15. Definition of done

- A lab assistant installs the CCC, then enrolls 20 mixed Windows and Linux PCs in under an hour using only the guides.
- Switching a session to Test mode blocks the seeded AI domains and suppresses Google AI Overview within seconds, on every enrolled PC.
- Starting `ollama`, installing an AI VS Code extension, tethering a phone via USB, and killing the agent each produce a visible alert on the dashboard within 10 seconds.
- Agent meets its CPU, memory, and bandwidth targets.
- Red-team harness produces the bypass table with no manual data entry.
- Privacy statement, consent template, and threat model are written and reviewed.
